## Полномочия по изменению исходников
<!-- Проставь режим в каждой строке. -->

Режимы: `изменять` — правишь сам; `по явному запросу` — правишь, только когда пользователь просит именно
эту правку; `только чтение` — не изменяешь, выдаёшь точную инструкцию для Конфигуратора или EDT.

| Вид исходника | Режим |
|---|---|
| Модули BSL основной конфигурации | `<изменять \| по явному запросу \| только чтение>` |
| XML: отчёты СКД | `<изменять \| по явному запросу \| только чтение>` |
| XML: макеты печатных форм | `<изменять \| по явному запросу \| только чтение>` |
| XML: формы собственных объектов | `<изменять \| по явному запросу \| только чтение>` |
| XML: метаданные объектов основной конфигурации (реквизиты, табличные части, типы) | `<изменять \| по явному запросу \| только чтение>` |
| XML: метаданные объектов расширений (заимствование типовых объектов, новые объекты и реквизиты) | `<изменять \| по явному запросу \| только чтение>` |
| XML: прочее (роли, обмены, подсистемы) | `<изменять \| по явному запросу \| только чтение>` |

- Таблица сильнее общих рекомендаций: при расхождении действует режим из таблицы.
- Что в таблице не значится — собственный код, он изменяется в обычном режиме: модули BSL расширений, внешних обработок и внешних отчётов. Режим типового кода на них не распространяется.
- `src\cf_vendor` не изменяется никогда: это эталон для сравнения, его обновляет пользователь.
- Изменяй XML только инструментом, который умеет проверить результат. Если такого инструмента в сессии нет — не изменяй XML: скажи об этом и выдай инструкцию для Конфигуратора или EDT.
- Изменяя XML, не трогай попутно другие объекты и другие части объекта; после изменения выполни проверку, предусмотренную инструментом.

## Работа с правилами
Правила из `.claude/rules/` получают и основная сессия, и твои субагенты. Исключение — встроенные субагенты Explore и Plan: они не получают ни `CLAUDE.md`, ни правил проекта, поэтому при делегировании им повторяй критичные ограничения прямо в тексте задания.

Правила с `paths:` подключаются в момент чтения подходящего файла, а не при старте сессии. Перед написанием BSL-кода перечитай `.claude/rules/1c-rules.md` инструментом Read — не полагайся на то, что видел его раньше.

## Разрешение конфликтов между скиллами
Скиллы находятся по своим `description`, и развязка пересекающихся пар живёт там же — в описаниях
обоих скиллов. Сюда попадает только то, чего в `description` быть не может: например, ограничение
на чужой скилл, чьё описание мы не правим.

## Принципы работы
- Минимальные изменения — только запрошенное, без scope creep
- Правило трёх ошибок: после 3 неудачных попыток одного подхода — остановись, опиши проблему, предложи другой подход
