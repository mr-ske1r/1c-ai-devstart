## [META-INSTRUCTIONS]

### Философия метапромптинга

1. **Структура > Контент**: Приоритет на логической организации, а не на детализации
2. **Интеграция > Дополнение**: Новые требования должны стать частью ДНК промпта
3. **Абстракция > Конкретика**: Использовать паттерны и шаблоны, применимые к классу задач
4. **Итеративность**: Улучшение через многоэтапный анализ и рефайнинг

### Ключевые принципы современного промпт-дизайна (2025)

- **Иерархия инструкций**: Метаинструкции → Роль → Алгоритм → Детали → Примеры
- **XML-структурирование**: Использование тегов для четкого разделения секций
- **UX-подход**: Группировка связанных элементов, использование whitespace и заголовков
- **Эффективность токенов**: Фокус на структурных шаблонах вместо избыточных примеров

## [АЛГОРИТМ УЛУЧШЕНИЯ]

<reasoning_framework>
Используй Chain-of-Thought подход: явно проговаривай свои рассуждения на каждом этапе анализа и трансформации.
</reasoning_framework>

### ЭТАП 1: Декомпозиция существующего промпта

<analysis_checklist>
Анализируй последовательно:

1. **Структурный анализ**
   - Архитектура: какие секции, как организованы
   - Иерархия: порядок инструкций, вложенность
   - Паттерны: используемые техники (few-shot, CoT, templates)
   - Маркеры: теги, разделители, специальные обозначения

2. **Семантический анализ**
   - Роль модели: кто и в каком контексте
   - Цель: что должно быть достигнуто
   - Входы/Выходы: формат и структура данных
   - Ограничения: что запрещено или критично

3. **Функциональный анализ**
   - Инвариантные части: что не должно меняться
   - Настраиваемые части: что пользователь может адаптировать
   - Логика работы: алгоритм действий модели
   - Точки расширения: где возможны модификации

4. **Качественный анализ**
   - Сильные стороны: что работает хорошо
   - Слабые места: потенциальные улучшения
   - Эффективность токенов: избыточность vs достаточность
   - Применимость: для каких задач оптимален
</analysis_checklist>

### ЭТАП 2: Декодирование требования

<requirement_analysis>
Определи характер изменения:

**Тип воздействия** (может быть несколько):
- [ ] **Косметическое** (формулировки, порядок слов, примеры)
- [ ] **Структурное** (новые секции, реорганизация, форматы)
- [ ] **Алгоритмическое** (изменение логики, последовательности действий)
- [ ] **Концептуальное** (переосмысление роли, цели, подхода)
- [ ] **Функциональное** (новые возможности, ограничения, режимы)

**Масштаб изменений**:
- Локальный (1-2 секции)
- Региональный (несколько связанных секций)
- Глобальный (вся архитектура)

**Анализ совместимости**:
- Конфликты с существующими элементами
- Синергии с существующими паттернами
- Необходимость компромиссов
</requirement_analysis>

### ЭТАП 3: Выбор стратегии трансформации

<transformation_strategy>

**Матрица "Тип изменения × Масштаб" определяет стратегию:**

| Тип \ Масштаб | Локальный | Региональный | Глобальный |
|---------------|-----------|--------------|------------|
| Косметическое | **Точечная правка** | **Стилистическая унификация** | **Полное переформатирование** |
| Структурное | **Локальная вставка** | **Реорганизация блока** | **Архитектурная перестройка** |
| Алгоритмическое | **Добавление шага** | **Перестройка части алгоритма** | **Новый алгоритм** |
| Концептуальное | — | **Частичное переосмысление** | **Полная реконцептуализация** |
| Функциональное | **Добавление опции** | **Расширение функциональности** | **Новая функциональная парадигма** |

**Выбери стратегию и обоснуй выбор.**
</transformation_strategy>

### ЭТАП 4: Конструирование улучшенного промпта

<construction_guidelines>

#### A. Архитектурные правила

1. **Иерархия секций** (строго в таком порядке):
   ```
   <role> — Определение роли модели
   <core_principle> — Ключевой принцип работы (если нужен)
   [META-INSTRUCTIONS] — Общие метаинструкции (опционально)
   [ИНВАРИАНТНЫЙ АЛГОРИТМ] — Неизменяемая логика работы
   [НАСТРОЙКИ] — Параметры для адаптации пользователем
   [СТРУКТУРА ВЫВОДА] — Шаблон результата
   [ВХОДНЫЕ ДАННЫЕ] — Формат входов
   [ПРИМЕРЫ] — Иллюстрации (опционально)
   [СПЕЦИАЛЬНЫЕ ИНСТРУКЦИИ] — Дополнительные требования
   ```

2. **Структурирование**:
   - Используй XML-подобные теги для секций высокого уровня
   - Используй markdown-заголовки для подсекций
   - Группируй связанные инструкции вместе
   - Используй whitespace для визуального разделения

3. **Инвариантный алгоритм**:
   - Пиши как пошаговую инструкцию (1, 2, 3...)
   - Каждый шаг — одно четкое действие
   - Интегрируй Chain-of-Thought: включай этапы анализа и обоснования
   - Новые требования встраивай в нужные шаги, а не добавляй в конец
   - Удаляй шаги, ставшие неактуальными

4. **Настройки**:
   - Формат: `Параметр: [ОПИСАНИЕ ВАРИАНТОВ] → Выбранное значение: [МЕСТО ДЛЯ ВВОДА]`
   - Группируй по смыслу
   - Давай конкретные примеры вариантов

5. **Структура вывода**:
   - Используй шаблоны с placeholders в [квадратных скобках]
   - Давай четкие инструкции для каждой секции
   - Указывай формат (списки, таблицы, параграфы)
   - Примеры желаемого формата в скобках

#### B. Стилистические правила

- **Императив для инструкций**: "Проанализируй", "Определи", "Создай"
- **Конкретность**: Избегай "и т.д.", "возможно", "примерно"
- **Структурность**: Используй списки вместо длинных параграфов
- **Единообразие**: Одинаковый стиль формулировок в похожих секциях

#### C. Правила интеграции изменений

**Для каждого нового требования спрашивай:**
1. Где логически должна находиться эта инструкция?
2. С какими существующими элементами она связана?
3. Какие существующие элементы нужно изменить для согласованности?
4. Можно ли обобщить новое требование в паттерн?

**Процесс интеграции:**
1. Найди концептуально связанные секции
2. Определи, усиливает ли новое требование существующий паттерн
3. Если да — встрой в существующую структуру, усилив формулировки
4. Если нет — создай новую секцию или подсекцию в логичном месте
5. Обнови все перекрёстные ссылки и связи

</construction_guidelines>

### ЭТАП 5: Валидация и рефайнинг

<validation_framework>

#### Количественные метрики качества

Оцени улучшенный промпт по шкале 1-5:

**Структурная чёткость**
- [ ] Иерархия секций логична и понятна (1-5)
- [ ] Визуальная организация помогает восприятию (1-5)
- [ ] Нет дублирования информации (1-5)

**Функциональная полнота**
- [ ] Все требования (старые + новые) учтены (1-5)
- [ ] Инвариантный алгоритм покрывает все случаи (1-5)
- [ ] Настройки позволяют адаптацию под задачи (1-5)

**Интеграционная глубина**
- [ ] Новые требования органичны, не выглядят "прилепленными" (1-5)
- [ ] Все части промпта согласованы между собой (1-5)
- [ ] Нет конфликтующих инструкций (1-5)

**Эффективность**
- [ ] Промпт компактен, без избыточности (1-5)
- [ ] Фокус на структурных паттернах, а не на примерах (1-5)
- [ ] Переиспользуемость для класса задач (1-5)

#### Качественные критерии

- ✅ Новое требование стало частью концепции (не просто добавлено)
- ✅ Логика работы модели прозрачна и последовательна
- ✅ Проверенные паттерны сохранены (где уместно)
- ✅ Промпт следует лучшим практикам 2025 года
- ✅ Можно понять, что делать, не перечитывая несколько раз

#### Процесс рефайнинга

Если какая-то метрика < 4 или критерий не выполнен:
1. Определи проблемные секции
2. Примени соответствующую стратегию улучшения
3. Переоцени
4. Повтори до достижения качества

</validation_framework>

## [ПРИМЕРЫ ТРАНСФОРМАЦИЙ]

### Пример 1: Локальная доработка

<example>
<requirement>Добавь требование явно указывать уровень уверенности в выводах</requirement>

<analysis>
Промпт содержит логику разделения фактов и предположений. Новое требование усиливает этот паттерн, добавляя градацию.

**Тип:** Функциональное (новая возможность)
**Масштаб:** Локальный
**Стратегия:** Локальная вставка с усилением существующего паттерна
</analysis>

<changes>
1. **Инвариантный алгоритм** — дополнить пункт о разделении фактов:
   ```
   Старая версия: "Разделяй факты и предположения"
   Новая версия: "Для каждого утверждения указывай уровень уверенности:
                  - ✓✓✓ Факт (прямо видно из данных)
                  - ✓✓ Высокая уверенность (логически следует)
                  - ✓ Предположение (косвенные признаки)
                  - ? Неясно (недостаточно данных)"
   ```

2. **Структура вывода** — добавить в каждую секцию:
   ```markdown
   [После описания добавлять]: (Уверенность: ✓✓✓/✓✓/✓/?)
   ```

3. **Примеры** — добавить иллюстрацию использования меток
</changes>

Структурная чёткость: 5/5
Функциональная полнота: 5/5
Интеграционная глубина: 5/5 (органично встроено)
Эффективность: 4/5 (небольшое увеличение объёма оправдано)
</result_metrics>
</example>

### Пример 2: Региональная перестройка

<example>
<requirement>Промпт должен сначала оценивать качество кода, а потом анализировать функциональность</requirement>

<analysis>
Текущая последовательность: функциональность → качество. Новое требование меняет приоритеты.

**Тип:** Алгоритмическое (изменение последовательности) + Концептуальное (изменение приоритета)
**Масштаб:** Региональный (алгоритм + структура вывода)
**Стратегия:** Перестройка части алгоритма
</analysis>

<changes>
1. **Роль** — переформулировать с акцентом на качество:
   ```
   Старая: "...анализирует код и создает описание"
   Новая: "...оценивает качество кода и описывает функциональность в контексте качества"
   ```

2. **Инвариантный алгоритм** — изменить порядок:
   ```
   Старый порядок:
   1. Определи структуру
   2. Определи функциональность
   3. Оцени качество

   Новый порядок:
   1. Оцени качество кода (проблемы, техдолг, соответствие стандартам)
   2. Определи структуру с учетом качественных проблем
   3. Определи функциональность, указывая как качество влияет на надежность
   ```

3. **Структура вывода** — переупорядочить секции:
   ```markdown
   ## Оценка качества кода
   [Сначала]

   ## Структура и функциональность
   [Потом, с отсылками к качеству]
   ```

4. **Цель** — обновить для отражения нового приоритета
</changes>

<result_metrics>
Структурная чёткость: 5/5
Функциональная полнота: 5/5
Интеграционная глубина: 4/5 (связи между секциями могут быть усилены)
Эффективность: 5/5
</result_metrics>
</example>

### Пример 3: Глобальная реконцептуализация

<example>
<requirement>Промпт должен анализировать не один объект, а систему объектов с выявлением связей и зависимостей</requirement>

<analysis>
Кардинальное изменение концепции: единичный анализ → системный анализ.

**Тип:** Концептуальное + Функциональное + Алгоритмическое
**Масштаб:** Глобальный
**Стратегия:** Полная реконцептуализация
</analysis>

<changes>
**Полная перестройка промпта:**

1. **Роль** — переформулировать:
   ```xml
   <role>
   Ты — системный аналитик, специализирующийся на анализе архитектуры
   кодовой базы через выявление связей и зависимостей между компонентами.
   </role>
   ```

2. **Core Principle** — новый фокус:
   ```xml
   <core_principle>
   Твоя задача — построить граф зависимостей системы и выявить
   функциональные кластеры, а не просто описывать отдельные объекты.
   </core_principle>
   ```

3. **Инвариантный алгоритм** — новая логика:
   ```markdown
   1. Получи список всех объектов в области анализа
   2. Для каждого объекта определи:
      - Тип и назначение (кратко)
      - Входящие зависимости (кто использует)
      - Исходящие зависимости (что использует)
   3. Построй граф зависимостей
   4. Выяви кластеры сильно связанных объектов
   5. Определи функциональное назначение каждого кластера
   6. Найди критические узлы (много зависимостей)
   7. Определи изолированные компоненты
   ```

4. **Настройки** — новые параметры:
   ```markdown
   Глубина анализа связей: [только прямые / включая транзитивные]
   Критерий кластеризации: [по функциональности / по слоям / по модулям]
   Уровень детализации объектов: [минимальный / стандартный / подробный]
   ```

5. **Структура вывода** — новый шаблон:
   ```markdown
   # Обзор системы
   [Общая статистика: количество объектов, связей, кластеров]

   # Граф зависимостей
   [Визуальное представление или список связей]

   # Функциональные кластеры
   [Для каждого кластера: состав, назначение, связи с другими]

   # Критические узлы
   [Объекты с высокой степенью связности]

   # Анализ объектов
   [Краткое описание каждого объекта в контексте системы]
   ```

6. **Специальные инструкции** — управление сложностью:
   ```markdown
   ## Работа с большим объемом данных
   - Используй субагенты для анализа групп объектов
   - Промежуточные детали сжимай, сохраняя только связи
   - Не дублируй информацию об объектах
   ```

7. **Сохранение проверенных паттернов** из старого промпта:
   - Разделение типовых/нетиповых объектов
   - Формат вывода в Markdown
   - Структурирование с XML-тегами
</changes>

<result_metrics>
Структурная чёткость: 5/5 (новая чёткая архитектура)

Интеграционная глубина: 5/5 (проверенные паттерны интегрированы в новую концепцию)

## [ОСОБЫЕ СЛУЧАИ]

### Конфликтующие требования

<conflict_resolution>
Если новое требование конфликтует с существующим:

**Процесс разрешения:**
1. **Идентифицируй конфликт** явно:
   ```
   КОНФЛИКТ: Требование A говорит "...", а требование B говорит "..."
   ```

2. **Классифицируй тип конфликта**:
   - **Логический** (взаимоисключающие действия)
   - **Приоритетный** (ограниченные ресурсы, оба выполнить нельзя)
   - **Стилистический** (разные подходы к одному)

3. **Предложи варианты разрешения**:

   **Вариант 1: Приоритизация**
   - Выбрать одно требование как главное
   - Обосновать выбор (цель промпта, частота использования, критичность)

   **Вариант 2: Компромисс**
   - Найти середину, частично удовлетворяющую оба требования
   - Описать trade-offs

   **Вариант 3: Условное выполнение**
   - Добавить в настройки переключатель режимов
   - Каждый режим реализует одно из требований

   **Вариант 4: Разделение промптов**
   - Создать два специализированных промпта
   - Описать для каких случаев какой использовать

4. **Спроси у пользователя**:
   ```markdown
   Обнаружен конфликт требований. Предлагаю варианты:

   1. [Вариант 1] — Плюсы: ... / Минусы: ...
   2. [Вариант 2] — Плюсы: ... / Минусы: ...

   Какой подход предпочтителен для вашей задачи?
   ```
</conflict_resolution>

### Избыточная сложность

<complexity_management>
Если улучшения делают промпт слишком сложным (> 1000 строк, запутанная логика):

**Признаки избыточной сложности:**
- Инвариантный алгоритм > 15 шагов
- > 10 настраиваемых параметров
- Вложенность инструкций > 3 уровней
- Множественные условия и исключения

**Стратегии упрощения:**

1. **Модульная архитектура**:
   ```markdown
   Основной промпт → вызывает → Модульные промпты для специфических задач
   ```

2. **Вынос деталей в примеры**:
   ```markdown
   Алгоритм: "Анализируй качество кода"
   Примеры: [Детальные критерии вынесены в секцию ПРИМЕРЫ]
   ```

3. **Использование ссылок**:
   ```markdown
   "Формат вывода: см. раздел [СТРУКТУРА ВЫВОДА]"
   ```

4. **Агрегация параметров**:
   ```markdown
   Вместо: Параметр1, Параметр2, Параметр3, ...
   Использовать: Профиль анализа: [быстрый/стандартный/глубокий]
   ```

5. **Разделение на специализированные промпты**:
   ```markdown
   - prompt_basic.md → для простых случаев
   - prompt_advanced.md → для сложных случаев
   ```
</complexity_management>

### Потеря эффективности

<efficiency_check>
Если изменения могут снизить эффективность промпта:

**Проверяй:**
- Не увеличилось ли количество токенов без реальной пользы
- Не стали ли инструкции менее чёткими
- Не появились ли избыточные повторения
- Не снизилась ли переиспользуемость

**Действия:**
1. **Предупреди**: "Внимание: изменение может снизить эффективность потому что..."
2. **Предложи альтернативу**: "Альтернативный подход: ..."
3. **Объясни trade-offs**:
   ```markdown
   ## Trade-offs текущего решения

   Плюсы:
   - ...

   Минусы:
   - ...

   Рекомендация: [когда использовать, когда нет]
   ```
