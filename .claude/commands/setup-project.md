# Первичная настройка проекта

Ты доводишь скопированный шаблон до рабочего состояния в проекте конкретной базы 1С.

## Правила выполнения

- **Команда идемпотентна.** Каждый запуск сверяет фактическое состояние и доделывает только
  недостающее. Уже настроенное не перезаписывай: покажи текущее значение и спроси, менять ли.
  Настройка рассчитана на личный проект одного разработчика: файлы-примеры превращаются
  в рабочие переименованием и в проекте не остаются.
- **Пароль от базы не запрашивай, не показывай и не записывай.** В файле настроек оставь пустое
  значение и скажи пользователю вписать его самому.
- **Не придумывай значения.** Если значение нельзя взять из исходников или получить от
  пользователя — оставь плейсхолдер и вынеси пункт в итоговый отчёт.
- **MCP в этой сессии недоступен**, даже если ты только что создал `.mcp.json`: серверы
  поднимаются при старте сессии. Проверок через MCP не планируй — предложи перезапуск в конце.
- Содержимое исходников не редактируй. Единственное, что тебе позволено с `src/`, — выгрузить
  туда конфигурацию и названные пользователем расширения на шаге 4 и переименовать каталог-
  заготовку `src/cfe_`.

## Шаг 2. Вопросы одним блоком

Спроси сразу всё, что не зависит от исходников. Остальное — конфигурация, релиз, режим
совместимости, префикс расширения — берётся из выгрузки на шаге 5, спрашивать это заранее
не нужно.

**Требуй ответ парами `КЛЮЧ = значение`, по одной паре на строку, и сам задавай вопросы
в этом же виде.** Свободный нумерованный список ненадёжен: пользователь пропускает пункт,
нумерация сдвигается, и значения встают не на свои места — на первом прогоне так поменялись
местами префикс конфигурации и компания.

Закрытые вопросы — где опубликован MCP-сервис, файловая база или серверная, контур базы,
инициализировать ли git, нужны ли маркеры доработок, какой набор полномочий — задавай выбором
вариантов, а не свободным текстом.

| Ключ | Что это |
|---|---|
| `ONEC_PATH` | путь к `1cv8.exe`; сначала найди сам (см. ниже) и предложи подтвердить |
| `BASE` | путь к файловой базе либо сервер и имя серверной базы |
| `USER` | имя пользователя 1С |
| `PUBLICATION` | имя публикации базы для MCP; для веб-сервера — ещё и адрес сервера |
| `MCP_SERVER` | имя MCP-сервера этой базы в `.mcp.json` (см. ниже) |
| `CIRCUIT` | контур базы: `тестовый` или `рабочий` |
| `MARKERS` | маркеры доработок: `везде`, `только типовой код основной конфигурации`, `не используются` (см. ниже) |
| `DEVELOPER` | имя разработчика для маркеров — не спрашивай при `MARKERS = не используются` |
| `PROJECT` | название проекта |
| `PREFIX` | префикс основной конфигурации |
| `COMPANY` | компания или проект для маркеров — не спрашивай при `MARKERS = не используются` |
| `TASK` | формат номера задачи: `dev-NNN`, `btrx-NNNN` или свой — не спрашивай при `MARKERS = не используются` |
| `EXTENSIONS` | точные имена расширений проекта, как в конфигураторе, либо «нет» |

**Маркеры доработок объясни, а не спрашивай кодом варианта.** `везде` — маркеры-комментарии
вокруг любой доработки, включая код в расширениях. `только типовой код основной конфигурации` —
маркеры лишь там, где код физически лежит внутри модулей вендора в `src\cf`; в расширениях,
внешних обработках и отчётах их нет. `не используются` — маркеров нет нигде, авторство
и история правок берутся из git и сравнения с `src\cf_vendor`; это выбор тех, кто ведёт
историю только в git (частый случай при работе в EDT). Назови и цену отказа: при обновлении
типовой конфигурации Конфигуратор показывает изменённые объекты, но свои строки внутри модуля
придётся искать диффом — а это работает, только если эталон `src\cf_vendor` в проекте
действительно поддерживается. По умолчанию предлагай `везде`.

Три ключа зависят от этого ответа, поэтому задай его в блоке первым и предупреди: ответил
`не используются` — `DEVELOPER`, `COMPANY` и `TASK` пропускай, они не понадобятся.

**Имя MCP-сервера предложи сам, а не спрашивай вслепую.** Собери его из конфигурации и контура
(`ut-test`, `buh-prod`) и дай подтвердить или заменить. Имя попадает в имя каждого инструмента
и при нескольких базах — единственное, чем они различаются в списке. Настраиваешь одну базу:
про остальные не спрашивай, пользователь добавит их сам строкой в `.mcp.json` и в паспорте.

**Путь к платформе ищи сам, а не спрашивай вслепую:** просмотри `C:\Program Files\1cv8`
и `C:\Program Files (x86)\1cv8`. Нашлась одна установка — предложи её; несколько — покажи
список с версией и разрядностью (`Program Files` — 64-разрядная, `(x86)` — 32-разрядная)
и дай выбрать; не нашлось ничего — спроси путь.

Пароль не спрашивай — см. «Правила выполнения».

## Шаг 3. Файлы окружения

1. `.gitignore.example` → `.gitignore` обычным переименованием. `git mv` не используй:
   репозитория может ещё не быть, а файлы шаблона в индекс не попадали.
2. `.mcp.json.example` → `.mcp.json` тем же способом. Вместо `<ИМЯ_СЕРВЕРА_БАЗЫ>` подставь
   `MCP_SERVER`. Адрес собери из ответов шага 2:
   локальная публикация — `localhost`, публикация на веб-сервере — названный адрес. Собери URL
   `http://<адрес>/<имя публикации>/hs/mcp/` и подставь вместо плейсхолдеров.
   Если MCP-сервис ещё не опубликован, оставь плейсхолдеры адреса и предупреди: сервер базы
   не заработает, пока в базу не установлено расширение
   [1c_mcp](https://github.com/vladimir-kharin/1c_mcp) и база с его HTTP-сервисом
   не опубликована на веб-сервере (подробности — скилл `mcp-1c`, секция «Подключение»).
3. `.claude/skills/1c-batch/assets/.1c-devbase.ps1.example` → **скопировать** в
   `tools/.1c-devbase.ps1` (пример остаётся на месте, он часть скилла). Заполни значениями
   `ONEC_PATH`, `BASE`, `USER` из шага 2; `$ONEC_PASSWORD` оставь пустым.
   **Записывай файл только PowerShell — `Set-Content -Encoding utf8BOM`, — а после записи
   проверь первые три байта: должны быть `EF BB BF`.** Обычный инструмент записи файлов
   создаёт UTF-8 без BOM; Windows PowerShell 5.1 читает такой `.ps1` как ANSI и молча портит
   кириллицу в имени пользователя. Ошибки при этом не возникает — поломка вылезет позже
   и будет выглядеть как отказ авторизации в базе.
4. `CLAUDE.local.md.example` → `CLAUDE.local.md` **переименованием** (тем же способом, что
   и `.gitignore`), затем подставь `DEVELOPER` из шага 2 вместо плейсхолдера. Файла и примера
   нет вовсе — создай `CLAUDE.local.md` сам: заголовок и строка с `DEVELOPER`.
   При `MARKERS = не используются` файл всё равно заведи, но плейсхолдер `<ИМЯ_РАЗРАБОТЧИКА>`
   оставь как есть: подставлять нечего, а файл пригодится для будущих личных параметров.
5. Если каталога `.git` нет — спроси, инициализировать ли репозиторий. Сам не инициализируй.
   Если `.git` есть, проверь `origin`: он должен вести на репозиторий проекта. Когда шаблон
   получен клонированием, `origin` указывает на репозиторий самого шаблона — предупреди, что
   проект привязан к чужому репозиторию и push уйдёт не туда, и предложи отвязать
   (`git remote remove origin`) или пересоздать репозиторий. Решение за пользователем, сам
   не выполняй.

## Шаг 4. Исходники в `src/`

Смотри на факт наличия файлов, а не на то, кто их выгрузил: пользователь мог выгрузить всё
сам заранее — тогда выгрузку пропусти и переходи сразу к уборке `.gitkeep` в конце шага.

**Конфигурация.** `src/cf/Configuration.xml` существует — ничего не делай. Иначе предложи
выгрузить через скилл `1c-batch` (`dump-config.ps1 src/cf`). Перед запуском напомни вписать
пароль в `tools/.1c-devbase.ps1`: без него конфигуратор не подключится к базе. Пользователь
отказался — не настаивай, значения паспорта из шага 5 просто спросишь.

**Расширения.** Имена ты уже получил ключом `EXTENSIONS` на шаге 2. **Сам список расширений
базы не выясняй и не перебирай:** ни `1c-batch`, ни MCP этого не умеют, а в типовой
конфигурации расширений поставщика могут быть десятки (багфиксы, локализация) — проекту они
не нужны.

Каталог для расширения — `src/cfe_` плюс имя **без ведущих подчёркиваний**: расширение
`_ДемоРасширение` кладётся в `src/cfe_ДемоРасширение`, а не в `src/cfe__ДемоРасширение`.
Точное имя, с подчёркиванием, нужно параметром команде выгрузки и строкой в паспорте — там
его не сокращай.

Для каждого расширения: `Configuration.xml` в его каталоге уже есть — пропусти, иначе выгрузи
`dump-extension.ps1 src/cfe_<каталог> <ТочноеИмяРасширения>`. Расширений в проекте нет —
иди дальше.

**Убери технические `.gitkeep` из наполнившихся каталогов.** Выполняй в любом случае, даже если
выгружать ничего не пришлось. Удали `src/cf/.gitkeep` и `.gitkeep` в каждом `src/cfe_*`, где
появились исходники: каталог больше не пустой, и заглушка стала мусором.

**Остальные `.gitkeep` не трогай** — ни в `docs/`, ни в `tools/`, ни в `src/cf_vendor`, `src/epf`,
`src/erf`, ни в ещё не выгруженном `src/cfe_*`. Git версионирует файлы, а не каталоги: без
заглушки эти каталоги не попадут в репозиторий и исчезнут при клонировании проекта на другую
машину, а паспорт `CLAUDE.md` ссылается на них как на каталоги исходников проекта. В `tools/`
заглушка нужна даже после шага 3: единственный файл каталога, `.1c-devbase.ps1`, закрыт
`.gitignore`.

## Шаг 5. Паспорт `CLAUDE.md`

Значения, которые можно не спрашивать, а предложить готовыми:

| Плейсхолдер | Откуда взять |
|---|---|
| `<КОНФИГУРАЦИЯ_И_РЕЛИЗ>` | `src/cf/Configuration.xml`: теги `Name`, `Vendor`, `Version` |
| `<РЕЖИМ_СОВМЕСТИМОСТИ>` | там же, тег `CompatibilityMode` |
| `<ВЕРСИЯ_ПЛАТФОРМЫ>` | из пути в `$ONEC_PATH` файла `tools/.1c-devbase.ps1` |
| `<ИМЯ_РАСШИРЕНИЯ>`, `<ПРЕФИКС_РАСШИРЕНИЯ>` | `Configuration.xml` в `src/cfe_*`: теги `Name` и `NamePrefix` |

Показывай найденное значение и спрашивай подтверждение, а не подставляй молча. Если исходники
не выгружались, спроси эти значения — теми же парами `КЛЮЧ = значение`.

`<НАЗВАНИЕ_ПРОЕКТА>`, `<ПРЕФИКС_КОНФИГУРАЦИИ>`, `<КОМПАНИЯ_ИЛИ_ПРОЕКТ>` и `TASK` у тебя уже
есть с шага 2 — повторно не спрашивай.

Секция «Маркеры доработок» зависит от ответа `MARKERS`:

- `везде` или `только типовой код основной конфигурации` — заполни `<КОМПАНИЯ_ИЛИ_ПРОЕКТ>`
  и формат `TASK`, остальное в секции оставь как есть;
- `не используются` — **удали секцию «Маркеры доработок» целиком**. Формат маркеров, компания
  и номер задачи в таком проекте не применяются, и держать их в паспорте значит занимать
  контекст агента мёртвыми фактами. То, что маркеров нет, он прочитает строкой в «Настройках
  проекта» — она остаётся в любом случае.

Секция «Настройки проекта»:

- **Маркеры доработок** — впиши ответ `MARKERS` дословно одним из трёх значений.
- **Стиль клиентской асинхронности.** По норме `1c-rules.md` `Асинх`/`Ждать` требуют платформы
  8.3.18 или выше. Смотри `<ВЕРСИЯ_ПЛАТФОРМЫ>`: ниже 8.3.18 — вариант один,
  `Показать* + ОписаниеОповещения`, так и напиши. Иначе спроси, какой стиль принят в проекте.
  На режим совместимости конфигурации не смотри: он доступность асинхронности не ограничивает.
- **Новые объекты метаданных** и **доработки типовых объектов** — спроси.

Секция «Подключённые базы (MCP)»: заполни единственную строку таблицы значениями `MCP_SERVER`,
конфигурации из паспорта и `CIRCUIT`. «Что разрешено» выведи из контура — `тестовый` даёт `всё`,
`рабочий` даёт `только чтение` — и покажи пользователю: режим он может поменять, но по умолчанию
рабочая база только читается. Пометку «по умолчанию» не ставь: база одна, и она единственная.

Каталоги расширений к этому моменту уже созданы шагом 4 — пустую заготовку `src/cfe_`
удали. Если выгрузки не было, переименуй заготовку в `src/cfe_<ИМЯ_РАСШИРЕНИЯ>`. На каждое
расширение проекта в таблице «Каталоги исходников проекта» должна быть своя строка.

## Шаг 6. Полномочия по изменению исходников

Набор пользователь выбрал на шаге 2. Покажи таблицу целиком и спроси, что поменять. Наборы —
отправная точка для разговора, а не стандарт: границы доверия к агенту определяет проект.

| Вид исходника | Осторожный | Рабочий | Полный доступ |
|---|---|---|---|
| Модули BSL основной конфигурации | по явному запросу | изменять | изменять |
| XML: отчёты СКД | только чтение | по явному запросу | изменять |
| XML: макеты печатных форм | только чтение | по явному запросу | изменять |
| XML: формы собственных объектов | только чтение | изменять | изменять |
| XML: метаданные объектов основной конфигурации | только чтение | по явному запросу | изменять |
| XML: метаданные объектов расширений | только чтение | по явному запросу | изменять |
| XML: прочее (роли, обмены, подсистемы) | только чтение | только чтение | по явному запросу |

По умолчанию предлагай «Осторожный»: доверие к агенту наращивают от меньшего, а расширить
полномочия можно в любой момент — достаточно поправить таблицу в `CLAUDE.md`.
Напомни: режим `изменять` для XML имеет смысл только там, где
есть инструмент, умеющий проверить результат, — иначе паспорт требует выдавать инструкцию для
Конфигуратора или EDT.

## Шаг 7. Отчёт

Перечисли:

1. что настроено и какими значениями; что выгружено в `src/`, а что там уже было;
2. что осталось сделать руками — **обязательно назови пароль в `tools/.1c-devbase.ps1`**;
3. **обязательно скажи про `src/cf_vendor`**: каталог остался пустым, а в паспорте он значится
   эталоном поставщика для сравнения — пока пользователь не положит туда копии типовых
   объектов до доработок, сравнивать будет не с чем;
4. какие плейсхолдеры остались незаполненными и почему;
5. что сессию нужно перезапустить, чтобы поднялись MCP-серверы, и что проверить после
   перезапуска: отвечает ли сервер из `MCP_SERVER` и совпала ли конфигурация с указанной
   в паспорте.

Если репозиторий инициализирован — покажи `git status` коротко: настройка почти всегда
оставляет незакоммиченные изменения (переименованные файлы окружения, заполненный паспорт,
а после выгрузки — тысячи файлов исходников). Скажи, что изменения не закоммичены, и предложи
сделать это первым коммитом проекта. **Сам коммит не делай** — только по команде пользователя.
