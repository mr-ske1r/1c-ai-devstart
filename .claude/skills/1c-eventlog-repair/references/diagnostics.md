# Диагностика: «Повреждение журнала», падение обработки БСП, журнал не пишется

## Симптом → вероятная причина

| Симптом | Сначала проверить |
|---|---|
| В форме журнала строки «Повреждение журнала» без даты, пользователь `<Неопределен>` | Смешение `.lgp` от разных словарей; битый `.lgp` после сторонней обрезки; устаревший `.lgx` |
| Обработка БСП падает: `Значение не является значением объектного типа (Свойство)` в `ОбщийМодуль.ЖурналРегистрации`, `Если СобытиеЖурнала.Данные.Свойство("Право")` | Запись, которую платформа считает `_$Access$_.AccessDenied`, а «Данные» у нее не структура. Почти всегда это чужая запись, прочитанная с чужим словарем |
| Журнал перестал пополняться | Один огромный `.lgp` (журнал без деления на периоды); после замены — проверить, что новые записи появились |
| Сбои после «обрезки» сторонней программой | Старый `.lgx` от исходного файла; оборванная последняя запись; испорченный заголовок |

## Падение БСП на `.Свойство("Право")` — разбор

В БСП 3.1 (`ОбщийМодуль.ЖурналРегистрации.ПрочитатьСобытияЖурналаРегистрации`):
```bsl
ИначеЕсли СобытиеЖурнала.Событие = "_$Access$_.AccessDenied" Тогда
    УстановитьСтрокуДанных(СобытиеЖурнала);   // Данные не меняет, только строковая копия
    Если СобытиеЖурнала.Данные <> Неопределено Тогда
        Если СобытиеЖурнала.Данные.Свойство("Право") Тогда   // ← падает, если Данные не Структура
```
Значит, падение возможно только на записи «Отказ в доступе» с «Данными» не-структурой. Номер строки
в тексте ошибки сверить по исходникам БСП той версии, что в базе.

Пример, как это выглядит. В копии рабочей базы рядом с журналом рабочей базы остался собственный
`.lgp` копии, записанный со старым словарем копии, а `1Cv8.lgf` заменили на словарь рабочей базы.
В старом словаре копии № 34 был ошибкой подсистемы «Подключаемые команды» с данными-строкой
`{"S","Отчет.ИмяОтчета"}`, в словаре рабочей базы № 34 — `_$Access$_.AccessDenied`.
Платформа честно отдала «Отказ в доступе» со строкой в «Данных», БСП упала. Сам очищенный файл был исправен.

Как найти виновные записи:
1. Платформой, не своим парсером: выгрузить `_$Access$_.AccessDenied` и проверить `ТипЗнч(Данные)`.
   - через MCP базы (`execute_code`, только чтение):
     ```bsl
     Т = Новый ТаблицаЗначений;
     ВыгрузитьЖурналРегистрации(Т, Новый Структура("Событие", "_$Access$_.AccessDenied"),
         "Дата,Данные,ИмяПользователя,Компьютер,ИмяПриложения,Сеанс");
     // перебрать Т, отобрать ТипЗнч(С.Данные) <> Тип("Структура") И С.Данные <> Неопределено
     ```
   - через COM: `scripts/Read-1CLog.vbs` (печатает «НЕ СТРУКТУРА» с датами).
2. По дате и сеансу найти запись в файлах: `scripts/Grep-LgpRecords.ps1 -DatePrefixes ... -Event <номер>`.
   Прогнать по каждому `.lgp` каталога: так видно, какой файл виноват. Подсказки на чужую запись:
   номера сеансов не того порядка (2, 9, 10 вместо десятков тысяч), незнакомые компьютеры и
   приложения, комментарий явно от другого события.
3. Проверить каждый `.lgp` на чужой словарь: `Filter-1CLog.ps1 -Mode Stats` с текущим `1Cv8.lgf`.
   В своем файле события `_$Transaction$_.Begin`/`Commit`/`Rollback` идут со статусами `C`, `R`, `U`;
   статус `N` у них — файл записан с другим словарем. `Diag-Lgp.ps1` такой файл не ловит, если текущий
   словарь больше «родного»: все номера в нем находятся, а значат другое.
4. Посмотреть время **создания** каждого `.lgp` и `.lgf` в ФС: файл, созданный одновременно с исходным
   словарем другой базы или копии, — подозреваемый. Файлы клиент-серверной базы лежат на сервере 1С —
   смотреть их там (например, по UNC-пути с разрешения пользователя), а не рассуждать заочно.

Лечение — убрать (перенести) чужой `.lgp` с его `.lgx` из `1Cv8Log`. Его записи до замены словаря
с текущим словарем не прочитать; исходный словарь копии, если затерт, не восстановить.

## «Повреждение журнала»

Это не записи файла: платформа вставляет такие строки сама, когда не может разобрать кусок `.lgp`
или сопоставить номера со словарем. Удалить их как записи нельзя — надо найти причину в файлах.
- Свой парсер (`scripts/Diag-Lgp.ps1`) ищет: нестандартное число полей, нечисловые ссылки, номера,
  которых нет в `.lgf`, даты назад. Чужой файл при словаре большего размера он не видит — для этого
  проверка статусов транзакций выше.
- Платформой (`scripts/Read-1CLog.vbs ... months`): выгрузка уровня «Ошибка» показывает
  «Повреждение журнала», помесячный счет записей сверяется со счетом парсера — провал показывает,
  где платформа перестала читать.

## Проверка на стенде, а не на рабочей базе

1. Пустая файловая база той же версии платформы:
   `1cv8.exe CREATEINFOBASE File="<каталог>" /Out <лог>` (запуск через `Start-Process` с готовой строкой
   аргументов — прямой вызов из PowerShell ломает кавычки). Дать базе один раз создать `1Cv8Log`.
2. Ее `1Cv8Log` переименовать целиком (мгновенно и обратимо), в новый `1Cv8Log` положить `1Cv8.lgf`
   проверяемой базы + проверяемый `.lgp`, без `.lgx`. Большой файл не копировать, а переносить
   (`Move-Item` в пределах тома) — места на второй экземпляр обычно нет; для проверки механизма
   хватает среза `-MaxBytes`. После проверки — вернуть исходный `1Cv8Log` и сверить состав и хеши.
3. `Read-1CLog.vbs <каталог базы> <с> <по> months` — индекс построится, затем выгрузка.
   Сумма помесячных счетчиков = число записей файла + записи, которые база написала о себе.
4. Код БСП: база с БСП (демо-БСП подходит), ее журнал сохранить в сторону, подложить проверяемый,
   `Test-BspEventLog.js "<строка соединения>" <дни>`; вернуть журнал и сверить хеши.
   Стенд дописывает свои записи в подложенный `.lgp` — этот экземпляр в рабочую базу уже не годится,
   итоговый файл собрать заново из исходника.

## Журнал не пишется

Один файл журнала в десятки гигабайт может перестать пополняться: записи прекращаются, `.lgx` перестает
обновляться. Очищенный файл того же журнала платформа пополняет нормально, поэтому лечение — замена
файла очищенным и деление журнала на периоды. После подселения обязательно проверить, что появились
свежие записи; если нет — искать причину дальше, а не считать работу законченной.
