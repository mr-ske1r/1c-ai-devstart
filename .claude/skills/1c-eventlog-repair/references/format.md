# Формат журнала регистрации 1С (старый, «1CV8LOG(ver 2.0)»)

Платформа называет его последовательным форматом. Устройство файлов `.lgp`/`.lgf` официально
не описано: все ниже — то, на что опираются скрипты скилла, а не контракт платформы.

## Состав каталога `1Cv8Log`

| Файл | Что это | Можно удалить? |
|---|---|---|
| `1Cv8.lgf` | Словарь: номер → имя пользователя, компьютера, события, объекта метаданных и т. д. Один на базу, общий для всех `.lgp`. | **Нет.** Без «своего» словаря записи `.lgp` бессмысленны. |
| `ГГГГММДДччммсс.lgp` | Сами записи, текст UTF-8. Имя — момент начала файла. | Только целиком, вместе с потерей его записей. |
| `ГГГГММДДччммсс.lgx` | Двоичный индекс к одноименному `.lgp`: где в файле лежат записи за какое время. | **Да.** Платформа строит его заново. |

- Где лежит: файловая база — `<каталог базы>\1Cv8Log`; клиент-сервер — `<каталог кластера>\reg_<порт>\<GUID базы>\1Cv8Log`
  на сервере 1С (обычно `...\srvinfo\reg_1541\...`).
- Формат SQLite (`1Cv8.lgd`) — другой случай, этот скилл к нему не относится. С 8.3.22 новые журналы в нем
  не создаются, его можно только читать или конвертировать в последовательный.
- Платформа дописывает новые записи в последний по имени `.lgp`; новый файл создает по настройке деления
  на периоды (час, день, неделя, месяц, год). Имя нового файла не обязательно равно текущей дате —
  по имени не судить, когда файл создан, смотреть время создания файла в ФС.

## `.lgf` — словарь

UTF-8 с BOM, заголовок `1CV8LOG(ver 2.0)`, GUID, пустая строка. Дальше элементы `{вид,...,номер},`.

| Вид | Что | Пример |
|---|---|---|
| 1 | пользователь | `{1,b823...,"ОтправкаСерверныхОповещений",2}` |
| 2 | компьютер | `{2,"SRV0",1}` |
| 3 | приложение | `{3,"BackgroundJob",2}` |
| 4 | событие | `{4,"_$Transaction$_.Rollback",24}` |
| 5 | объект метаданных | `{5,a9f3...,"РегламентноеЗадание.УдалениеФайловВременногоХранилища",1}` |
| 6 | имя сервера | `{6,"SRV0",1}` |
| 7, 8 | основной и вспомогательный порт | `{7,1560,1}` |
| 9 | разделитель | `{9,530a...,"ОбластьДанныхВспомогательныеДанные",1}` |
| 10–13 | значения разделения сеанса и т. п.; бывают многострочными | `{11,\r\n{2,1,1,2,1},131}` |

- Словарь **только дописывается**: новые элементы в конец, номера существующих не меняются. Поэтому
  более свежий `.lgf` той же базы совместим со всеми ее старыми `.lgp`.
- Номера свои у каждой базы. Словарь другой базы (даже копии, развернутой из бэкапа и поработавшей
  самостоятельно) с чужими `.lgp` несовместим: номера совпадут, имена — нет.
- GUID в заголовке `.lgf` не обязан совпадать с GUID в заголовке `.lgp` — это не признак ошибки.
- Номер события по имени ищется регуляркой `\{4,"((?:[^"]|"")*)",(\d+)\}`. Не хардкодить номера:
  в другой базе `_$Transaction$_.Rollback` будет другим числом.

## `.lgp` — записи

Начало файла:
```
﻿1CV8LOG(ver 2.0)\r\n<GUID>\r\n\r\n{запись},\r\n{запись},\r\n...{последняя запись}
```
Разделитель записей `,\r\n`; у последней записи запятой нет. Пример записи:
```
{20260804013011,N,
{0,0},1,1,2,41971039,182,W,"Пространство блокировки: ...",0,
{"R",52000:aa14a036bc7426ae11f092f64f3df0c8},"Уведомление о статусе ...",1,7,0,71370,0,
{2,1,1,2,1}
}
```

| № поля | Что | Примечание |
|---|---|---|
| 0 | дата `ГГГГММДДччммсс` | локальное время сервера |
| 1 | статус транзакции, буква | `N` — вне транзакции; встречаются `C`, `R`, `U`. Расшифровка букв официально не описана — по смыслу буквы не судить. Устойчиво одно: у событий `_$Transaction$_.*` статуса `N` не бывает |
| 2 | транзакция `{дата16,номер16}` | `{0,0}` — вне транзакции |
| 3 | пользователь | вид 1 словаря, 0 — не задан |
| 4 | компьютер | вид 2 |
| 5 | приложение | вид 3 |
| 6 | номер соединения | |
| 7 | событие | вид 4 |
| 8 | важность | `I` информация, `W` предупреждение, `E` ошибка, `N` примечание |
| 9 | комментарий | строка в кавычках, может быть многострочной |
| 10 | метаданные | вид 5 (или `{...}` для нескольких) |
| 11 | данные | `{"U"}` неопределено, `{"S","…"}` строка, `{"R",таблица:guid}` ссылка, `{"N",…}`, `{"B",…}`, `{"P",{…}}` структура-описание |
| 12 | представление данных | строка |
| 13, 14, 15 | сервер, основной порт, вспомогательный порт | виды 6, 7, 8 |
| 16 | номер сеанса | |
| 17… | у большинства записей `0`; у `_$Access$_.AccessDenied` — от 1 до 6 дополнительных чисел | всего полей 19, у «Отказа в доступе» до 24 |
| последнее | `{...}` разделение данных сеанса | |

Связанную пустую транзакцию фильтр узнает по именам событий `Begin`/`Rollback` из словаря, а букву
статуса `R` проверяет как дополнительный признак. Если «связанных транзакций» в отчете 0, а в выписке
записей пары `Begin`/`Rollback` перед мусором видны — сначала посмотреть, какая у них буква статуса.

Правила разбора:
- Строки в кавычках, кавычка внутри удваивается (`""`). Внутри строк бывают `\r\n`, `{`, `}` и запятые.
- Запись = от `{` на нулевой глубине до парной `}`, скобки внутри кавычек не считать. Удвоенная кавычка
  переключает состояние «внутри строки» дважды — разбор по четности кавычек это переживает.
- Платформа изредка пишет эмодзи суррогатной парой с голой кавычкой: `\d83d"\dd25`. Поля такой записи
  разъезжаются, но граница записи определяется верно. Если «нарушений структуры» вдруг много — смотреть
  такие места.
- Даты почти монотонны; «назад» на секунды–минуты бывает (параллельная запись) — это норма. Поэтому
  двоичный поиск по дате внутри `.lgp` ненадежен: искать записи только последовательным проходом.

## `.lgx` — индекс

Двоичный, формат не документирован, около десятой части размера `.lgp`. Хранит байтовые смещения
внутри `.lgp`, поэтому:
- после любого изменения `.lgp` (вырезали записи, обрезали хвост) старый `.lgx` указывает «в никуда» —
  вероятная причина сбоев журнала после сторонних «обрезалок»;
- отсутствующий `.lgx` платформа строит сама при чтении журнала — и в клиент-серверной, и в файловой
  базе; на файле в десятки гигабайт — минуты. Пустой (0 байт) или отсутствующий `.lgx` — не признак
  проблемы.
