## Паттерн: замена коррелированного подзапроса в списке полей

> Норма — в `.claude/rules/1c-rules.md`. Здесь — один из вариантов переписывания.

**Почему:** коррелированный подзапрос в списке полей `ВЫБРАТЬ` создаёт риск повторной обработки данных для строк результата. Соединение с агрегацией иногда устраняет этот риск, но не является универсально эквивалентной заменой: проверь дубли строк, группировку и обработку `NULL`.

### Неправильно — коррелированный подзапрос в списке полей

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   Заказы.Ссылка КАК Заказ,
|   (ВЫБРАТЬ СУММА(Строки.Сумма) ИЗ Документ.ЗаказКлиента.Товары КАК Строки
|    ГДЕ Строки.Ссылка = Заказы.Ссылка) КАК ИтогоПоЗаказу  // выполняется на КАЖДУЮ строку
|ИЗ
|   Документ.ЗаказКлиента КАК Заказы";
```

### Возможная замена — LEFT JOIN + СГРУППИРОВАТЬ

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   Заказы.Ссылка КАК Заказ,
|   СУММА(ЕСТЬNULL(Строки.Сумма, 0)) КАК ИтогоПоЗаказу
|ИЗ
|   Документ.ЗаказКлиента КАК Заказы
|       ЛЕВОЕ СОЕДИНЕНИЕ Документ.ЗаказКлиента.Товары КАК Строки
|       ПО Строки.Ссылка = Заказы.Ссылка
|СГРУППИРОВАТЬ ПО
|   Заказы.Ссылка";
```

`В (&Список)` — условие вхождения с параметром, а не подзапрос. Подзапросы и соединения с ними оценивай отдельно по семантике и объёму данных; соединения с вложенными запросами обычно выноси во временные таблицы, кроме гарантированно малых наборов.

## Паттерн: соединение с вложенным запросом → временная таблица (std#655)

> Норма — в `.claude/rules/1c-rules.md`. Источник: [std#655](https://v8std.ru/std/655/).

**Почему:** соединение с вложенным запросом СУБД выполняет крайне нестабильно по скорости; план зависит от статистики и различается между СУБД. Соединяй только объекты метаданных или временные таблицы. Исключение — вложенный запрос гарантированно сканирует мало записей.

### Неправильно — соединение с вложенным запросом

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   Заказы.Ссылка КАК Заказ,
|   Оплаты.Сумма КАК Оплачено
|ИЗ
|   Документ.ЗаказКлиента КАК Заказы
|       ЛЕВОЕ СОЕДИНЕНИЕ
|           (ВЫБРАТЬ Док.Заказ КАК Заказ, СУММА(Док.Сумма) КАК Сумма
|            ИЗ Документ.ПоступлениеОплаты КАК Док
|            СГРУППИРОВАТЬ ПО Док.Заказ) КАК Оплаты
|       ПО Оплаты.Заказ = Заказы.Ссылка";
```

### Правильно — вынести во временную таблицу

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   Док.Заказ КАК Заказ,
|   СУММА(Док.Сумма) КАК Сумма
|ПОМЕСТИТЬ втОплаты
|ИЗ
|   Документ.ПоступлениеОплаты КАК Док
|СГРУППИРОВАТЬ ПО
|   Док.Заказ
|ИНДЕКСИРОВАТЬ ПО
|   Заказ
|;
|////////////////////////////////////////////////////////////////////////////////
|ВЫБРАТЬ
|   Заказы.Ссылка КАК Заказ,
|   ЕСТЬNULL(втОплаты.Сумма, 0) КАК Оплачено
|ИЗ
|   Документ.ЗаказКлиента КАК Заказы
|       ЛЕВОЕ СОЕДИНЕНИЕ втОплаты
|       ПО втОплаты.Заказ = Заказы.Ссылка";
```

**Важно про эквивалентность:** вложенные и последовательные соединения — разные запросы и могут давать разный результат. При переписывании проверяй дубли строк, группировку и обработку `NULL`.

## Паттерн: обработка NULL в LEFT JOIN

**Почему:** `ЛЕВОЕ СОЕДИНЕНИЕ` возвращает NULL для полей правой таблицы, если нет соответствия. В 1С NULL — это особое значение: `NULL + 100 = NULL`, `NULL > 0 = ЛОЖЬ`. Необработанный NULL приводит к:
1. Неверным расчётам (сумма с NULL = NULL)
2. Потерянным строкам в условиях (NULL не проходит условие `> 0`)
3. Ошибкам при дальнейшей обработке в коде

### Правильно — ЕСТЬNULL()

```bsl
Запрос.Текст =
"ВЫБРАТЬ
|   Номенклатура.Ссылка КАК Номенклатура,
|   Номенклатура.Наименование КАК Наименование,
|   ЕСТЬNULL(ОстаткиТоваров.КоличествоОстаток, 0) КАК Остаток,
|   ЕСТЬNULL(ОстаткиТоваров.СуммаОстаток, 0) КАК СуммаОстатка
|ИЗ
|   Справочник.Номенклатура КАК Номенклатура
|       ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ТоварыНаСкладах.Остатки КАК ОстаткиТоваров
|       ПО Номенклатура.Ссылка = ОстаткиТоваров.Номенклатура
|ГДЕ
|   ЕСТЬNULL(ОстаткиТоваров.КоличествоОстаток, 0) > 0";
```

### Неправильно

```bsl
// ПЛОХО: без ЕСТЬNULL при LEFT JOIN — числовые поля могут быть NULL
Запрос.Текст =
"ВЫБРАТЬ
|   Номенклатура.Наименование,
|   ОстаткиТоваров.КоличествоОстаток КАК Остаток  // Будет NULL, если нет остатков!
|ИЗ
|   Справочник.Номенклатура КАК Номенклатура
|       ЛЕВОЕ СОЕДИНЕНИЕ РегистрНакопления.ТоварыНаСкладах.Остатки КАК ОстаткиТоваров
|       ПО Номенклатура.Ссылка = ОстаткиТоваров.Номенклатура
|ГДЕ
|   ОстаткиТоваров.КоличествоОстаток > 0";  // NULL > 0 = ЛОЖЬ → строки без остатков пропадут!
```

## Паттерн: ВЫРАЗИТЬ — для оптимизации составных типов

**Почему:** Если поле имеет составной тип (например, «Регистратор» регистра может быть любым документом), СУБД выполняет LEFT JOIN ко ВСЕМ таблицам составного типа. `ВЫРАЗИТЬ(Поле КАК Тип)` ограничивает соединения только указанным типом, радикально улучшая производительность.

**Стандарт ИТС:** «Использование конструкции ВЫРАЗИТЬ в запросах».

### Правильно

```bsl
// ВЫРАЗИТЬ — ограничиваем тип, СУБД делает JOIN только с одной таблицей
Запрос.Текст =
"ВЫБРАТЬ
|   Движения.Период,
|   ВЫРАЗИТЬ(Движения.Регистратор КАК Документ.РеализацияТоваровУслуг).Контрагент КАК Контрагент,
|   Движения.Количество
|ИЗ
|   РегистрНакопления.ТоварыНаСкладах КАК Движения
|ГДЕ
|   Движения.Регистратор ССЫЛКА Документ.РеализацияТоваровУслуг";
```

### Неправильно

```bsl
// ПЛОХО: обращение к реквизиту через составной тип без ВЫРАЗИТЬ
// СУБД сделает LEFT JOIN к КАЖДОМУ типу, входящему в «Регистратор»
Запрос.Текст =
"ВЫБРАТЬ
|   Движения.Период,
|   Движения.Регистратор.Контрагент КАК Контрагент,
|   Движения.Количество
|ИЗ
|   РегистрНакопления.ТоварыНаСкладах КАК Движения";
// Если Регистратор может быть 20 видами документов — это 20 LEFT JOIN!
```

### Альтернатива — ВЫБОР/КОГДА, если известно несколько конкретных типов

Если составное поле принимает несколько заранее известных типов и по каждому нужна своя логика — `ВЫБОР КОГДА ... ССЫЛКА Тип ТОГДА ВЫРАЗИТЬ(...) ... КОНЕЦ` читается лучше набора отдельных `ВЫРАЗИТЬ`. Это пример, а НЕ универсальная замена `ВЫРАЗИТЬ` (для одного типа `ВЫРАЗИТЬ` проще).

```bsl
|   ВЫБОР
|       КОГДА Движения.Регистратор ССЫЛКА Документ.РеализацияТоваровУслуг
|           ТОГДА ВЫРАЗИТЬ(Движения.Регистратор КАК Документ.РеализацияТоваровУслуг).Контрагент
|       КОГДА Движения.Регистратор ССЫЛКА Документ.ВозвратТоваровОтПокупателя
|           ТОГДА ВЫРАЗИТЬ(Движения.Регистратор КАК Документ.ВозвратТоваровОтПокупателя).Контрагент
|   КОНЕЦ КАК Контрагент
```

## Паттерн: условие соединения (ПО) vs условие ГДЕ в LEFT JOIN

**Почему:** В `ЛЕВОМ СОЕДИНЕНИИ` условие в `ГДЕ` и условие в `ПО` работают по-разному:
- Условие в `ПО` фильтрует **правую** таблицу ДО соединения — строки левой таблицы без пары остаются с NULL
- Условие в `ГДЕ` фильтрует **результат** ПОСЛЕ соединения — строки с NULL отбрасываются, превращая LEFT JOIN в INNER JOIN

### Правильно

```bsl
// Фильтр правой таблицы — в условии ON
Запрос.Текст =
"ВЫБРАТЬ
|   Номенклатура.Наименование,
|   ЕСТЬNULL(Цены.Цена, 0) КАК Цена
|ИЗ
|   Справочник.Номенклатура КАК Номенклатура
|       ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.ЦеныНоменклатуры.СрезПоследних(&ДатаЦен,
|           ВидЦены = &ВидЦены) КАК Цены
|       ПО Номенклатура.Ссылка = Цены.Номенклатура";
// Все товары будут в результате, даже без цены
```

### Неправильно

```bsl
// ПЛОХО: фильтр по правой таблице в WHERE — LEFT JOIN фактически стал INNER JOIN
Запрос.Текст =
"ВЫБРАТЬ
|   Номенклатура.Наименование,
|   Цены.Цена
|ИЗ
|   Справочник.Номенклатура КАК Номенклатура
|       ЛЕВОЕ СОЕДИНЕНИЕ РегистрСведений.ЦеныНоменклатуры.СрезПоследних КАК Цены
|       ПО Номенклатура.Ссылка = Цены.Номенклатура
|ГДЕ
|   Цены.ВидЦены = &ВидЦены";  // Строки без цены (NULL) — отфильтруются!
```
