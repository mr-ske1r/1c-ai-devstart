# Адверсарное ревью со структурированным результатом

Родное `codex exec review` отвечает на вопрос «что не так в коде». Адверсарное ревью отвечает
на другой: «почему это изменение нельзя выпускать» — оно оспаривает замысел, допущения
и поведение под нагрузкой, а не только дефекты реализации. Применяй, когда пользователь просит
«разнеси», «найди дыры», «оспорь дизайн», «что сломается в бою».

## Запуск

```bash
codex exec -s read-only --skip-git-repo-check -C "$PWD" \
  --output-schema "$СКИЛЛ/references/review-schema.json" -o "$ОТВЕТ" - <<'EOF'
<шаблон ниже с заполненными полями>
EOF
```

`$СКИЛЛ` — каталог этого скилла: `.claude/skills/codex-cli` в проекте либо
`~/.claude/skills/codex-cli`, если скилл подключён на уровне пользователя. Путь к схеме нужен
абсолютный. Ответ в `$ОТВЕТ` — JSON строго
по схеме: `verdict` (`approve` | `needs-attention`), `summary`, `findings[]` с полями `severity`,
`title`, `body`, `file`, `line_start`, `line_end`, `confidence`, `recommendation`, и `next_steps[]`.
Читай его как данные, а не как текст: сортируй по `severity`, показывай `confidence`.

**Схема работает только с обычным `exec`.** Подкоманда `review` флаг `--output-schema` молча
игнорирует и отдаёт свой текст: вводный абзац, затем `Full review comments:` со строками
`[P1]`/`[P2]` и адресом `файл:строки`.

Под `-s read-only` Codex сам выполняет читающие команды git и видит диф — вкладывать диф в промпт
не нужно. Цель ревью называй в `<task>` словами: «незакоммиченные изменения», «ветка против
master», «коммит <sha>».

## Шаблон

Теги — стабильные имена блоков, содержимое — по-русски. Заполни `<task>` и фокус, остальное
оставь как есть; сокращай, только если пользователь просит другой охват.

```
<role>
Ты выполняешь адверсарное ревью изменения в конфигурации 1С:Предприятие 8. Твоя задача —
подорвать доверие к изменению, а не подтвердить его.
</role>

<task>
Рассмотри <цель: незакоммиченные изменения | ветку против <база> | коммит <sha>> так, будто
ищешь самые сильные причины, по которым это изменение нельзя выпускать.
Фокус пользователя: <что именно его беспокоит, или «не задан»>.
</task>

<operating_stance>
По умолчанию — скепсис. Считай, что изменение ломается неочевидным и дорогим способом, пока
доказательства не покажут обратное. Не засчитывай добрые намерения, частичные исправления
и «потом доделаем». Работает только на счастливом пути — это дефект.
</operating_stance>

<attack_surface>
В первую очередь ищи дорогие, опасные и трудно обнаружимые отказы, характерные для 1С:
- транзакции и блокировки: запись вне транзакции, чтение остатков без управляемой блокировки,
  потерянные обновления при параллельной работе, обращение к базе после отката
- проведение: движения при перепроведении и отмене проведения, оперативный и неоперативный
  режим, контроль остатков
- права и RLS: обход через привилегированный режим, запросы без РАЗРЕШЕННЫЕ там, где нужны
- обмен и загрузка: ОбменДанными.Загрузка, дубли при повторной загрузке, идемпотентность
- регламентные и фоновые задания: повторный запуск, зависание, отсутствие журналирования
- обновление и совместимость: расширение при смене версии типовой, объекты на поддержке,
  миграция данных
- производительность: запросы и серверные вызовы в цикле, обращение через точку в цикле,
  соединения с вложенными запросами
- обработка исключений: Попытка без реакции, потеря контекста ошибки, продолжение после сбоя
</attack_surface>

<review_method>
Активно пытайся опровергнуть изменение. Ищи нарушенные инварианты, отсутствующие проверки,
необработанные пути отказа и допущения, которые перестают быть верными под нагрузкой.
Проследи, как плохие данные, повторы, параллельные действия и частично выполненные операции
проходят через код. Диф и файлы читай командами git и чтения файлов.
</review_method>

<finding_bar>
Сообщай только существенные находки. Не включай стиль, именование, мелкую уборку и предположения
без доказательств. Каждая находка отвечает на четыре вопроса: что может пойти не так; почему этот
путь уязвим; каковы последствия; какое конкретное изменение снизит риск.
</finding_bar>

<structured_output_contract>
Верни только валидный JSON по предоставленной схеме. Текст полей — по-русски.
`needs-attention` — если есть хоть один существенный риск, ради которого стоит остановить
выпуск. `approve` — только если ни одной обоснованной адверсарной находки нет.
summary — резкая оценка «выпускать / не выпускать», а не нейтральный пересказ.
</structured_output_contract>

<grounding_rules>
Будь агрессивен, но опирайся на факты. Каждая находка должна быть защитима по коду или выводу
инструментов. Не выдумывай файлы, строки, пути выполнения и поведение платформы, которых
не можешь подтвердить. Вывод опирается на предположение — скажи это в теле находки и не завышай
уверенность.
</grounding_rules>

<calibration_rules>
Одна сильная находка лучше нескольких слабых. Не разбавляй серьёзное филлером. Изменение
выглядит безопасным — скажи прямо и верни пустой список.
</calibration_rules>
```

## После ответа

Находки показываются пользователю дословно, в порядке серьёзности, с уверенностью. Ничего
из них не чинится, пока пользователь не скажет, что именно чинить: ревью — это мнение,
а не задание.
