## Инвентаризация

Сначала исследуй проект по `.claude/rules/mcp.md`, потом задавай вопросы.

| Факт | Как получить | Зачем |
|---|---|---|
| релиз технологической платформы | паспорт проекта, база или среда | проверить фактическую доступность механизмов |
| `Режим совместимости` конфигурации | свойства конфигурации | статья требует `Версия8_3_7` или выше; не путать с интерфейсом |
| `Режим совместимости интерфейса` | свойства конфигурации | определить исходное состояние и переходный режим |
| поддержка конфигурации и расширения | исходники/метаданные | оценить допустимые точки изменений и стоимость сопровождения |
| основные, дополнительные и изменённые формы/макеты | метаданные и исходники | определить объём и кандидатов на дублирование |
| общие формы, открываемые по имени | поиск вызовов | для отдельной 8.5-формы потребуются изменения точек открытия |
| EPF/ERF | каталоги проекта | они не должны выпасть из инвентаризации интерфейса |
| динамическое изменение форм | поиск BSL | оценить риск поддержки и производительности |
| целевые клиенты, рабочие места и категории пользователей | проект и постановка | выбрать очередь пилота |
| версия БСП | только если формы или переход зависят от БСП | не собирать нерелевантный факт |

Не фиксируй минимальный релиз платформы по памяти: проверяй наличие свойства и механизмов в
фактической среде или актуальной официальной справке. Требование `РежимСовместимости >=
Версия8_3_7` относится к свойству конфигурации, а не к номеру установленной платформы.

## Переходные режимы и запуск

| Режим совместимости интерфейса | Интерфейс по умолчанию | Назначение |
|---|---|---|
| `Такси. Разрешить Версия 8.5` | «Такси» | подготовка и пилот без массового переключения |
| `Версия 8.5. Разрешить Такси` | «Версия 8.5» | основной интерфейс уже 8.5, «Такси» остаётся для отката |

Принудительный запуск:

- тонкий/толстый клиент: `/iTaxi`, `/i85`;
- веб-клиент: `?iTaxi`, `?i85`.

Не полагайся только на значение по умолчанию: ранее сохранённые настройки клиентского приложения
могут оставить пользователю «Такси» после переключения режима. У платформы нет стандартного
пользовательского диалога смены интерфейса; механизм выбора и политика переключения должны быть
частью плана внедрения.

Программное изменение `НастройкиКлиентскогоПриложения` — отдельное техническое решение. Не
вставляй код автоматически: передай реализацию в `form-work` и учитывай, что настройки хранятся
для клиента.

## Дополнительные формы

Форма получает свойство `Использование в режиме совместимости интерфейса`:

- `Любой`;
- `Версия 8.5`;
- `Такси`.

Платформа выбирает основную или дополнительную форму так:

1. Есть только одна форма — выбирает её.
2. У обеих одинаковая совместимость — выбирает основную.
3. Значения различаются — выбирает форму, лучше соответствующую текущему интерфейсу.

После создания отдельной формы 8.5 помести её в соответствующее свойство дополнительной формы
объекта. Для общих форм и форм, открываемых по имени из BSL, найди и пересмотри все точки открытия:
автоматический подбор объекта метаданных их не заменяет.

## Конвертер и порядок формы

1. Установи `Такси. Разрешить Версия 8.5`; пользователи продолжают работать в «Такси».
2. Для разработчика включи просмотр/редактирование и тестовый запуск в 8.5.
3. Включи свойство конфигурации `Режим перехода на интерфейс "Версия 8.5"`.
4. Открой форму/макет в новом интерфейсе и оцени desktop, тёмную тему и нужный мобильный клиент.
5. Запусти проверку и конвертацию сначала для конкретной формы либо для конфигурации через
   рефакторинг.
6. Проверь каждое автоматическое изменение и вручную доведи форму по `form-design.md` и
   `visual-style.md`.
7. Проверь форму в обоих интерфейсах, если она остаётся общей.

Не компенсируй разницу массовым программным перестроением формы в `1С:Предприятии`: это ухудшает
поддержку и скорость. Малую прикладную динамику оцени отдельно, но архитектурное различие
интерфейсов выражай свойствами или отдельными формами.

## Одна или две формы

```text
Открыть существующую форму в 8.5
├─ Выглядит приемлемо без больших изменений?
│  ├─ Да → конвертер → малые правки → проверка обоих интерфейсов
│  │       ├─ Оба приемлемы → одна форма [DUAL-TAXI-85]
│  │       └─ Один неприемлем → две формы
│  └─ Нет → две формы
└─ Для макета применяется то же дерево решения
```

При двух формах:

- существующую ограничь значением `Такси`;
- новую или копию — `Версия 8.5`;
- для копии запусти конвертер; новую с нуля создавай сразу для интерфейса 8.5;
- перенеси прикладную логику осознанно и проверь точки вызова;
- не допускай независимого расхождения бизнес-логики без отдельного архитектурного решения.

Одна форма уменьшает объём и сопровождение, но пользователи «Такси» видят промежуточные изменения.
Две формы изолируют переход, но увеличивают конфигурацию, тестовую матрицу и стоимость поддержки.

## Четыре подхода к дублированию

| Подход | Что делаем | Цена и когда выбирать |
|---|---|---|
| 1. Минимум копий, минимальные правки общих форм | большинство форм общие, улучшения ограничены | самый дешёвый переход, важна стабильность «Такси» |
| 2. Минимум копий, активные улучшения после общего переключения | сначала умеренная адаптация, затем развитие 8.5 | переход дешевле, но изменения продолжаются после релиза |
| 3. Минимум копий, активная переделка общих форм сразу | пользователи «Такси» видят существенные изменения | допустим ранний визуальный сдвиг, не нужны ограничения развития |
| 4. Активное дублирование | отдельные формы для интерфейсов | максимальная свобода и изоляция, максимальная стоимость поддержки |

Не выбирай подход один раз для всей конфигурации автоматически. Решай по форме/макету с учётом
сложности, частоты использования, кастомизаций и приемлемости изменений для пользователей.

## Очередность конфигурации

| Стратегия | Когда подходит | Пилот |
|---|---|---|
| по рабочим местам | можно завершить полный сценарий роли | группа пользователей конкретного рабочего места |
| наиболее частые формы | небольшая конфигурация | пользователи главных форм |
| частые формы выбранной категории | большая конфигурация | одна категория пользователей |
| постепенная подготовка всей конфигурации | тиражное решение без оперативного переключения пользователей | пользователи остаются в «Такси» до общей готовности |

В поставке поэтапного тиражного решения формы 8.5 могут временно не включаться до готовности, но
исходники и статус работ должны оставаться контролируемыми.

## Пилот, переключение и очистка

### Пилот

- зафиксируй рабочие места, формы, пользователей и критерии готовности;
- запускай пилот с `/i85` или политикой клиентских настроек;
- собери дефекты по сценариям, темам и клиентам;
- откат — запуск в «Такси», а не отмена всех адаптаций.

### Основное переключение

Когда большинство форм готово, установи `Версия 8.5. Разрешить Такси` и включи 8.5 всем
пользователям. Сохрани возможность временного возврата в «Такси» до выполнения критериев
стабильности.

### Окончательная очистка

Только после периода работы всех пользователей в 8.5:

- удали формы и макеты только для «Такси»;
- удали варианты общих картинок для старого интерфейса, а варианты 8.5 переведи в `Любой`, где
  это корректно;
- удали BSL-ветвления выбора формы по текущему интерфейсу;
- установи `Режим совместимости интерфейса = Версия 8.5`;
- повторно проверь внешние обработки, отчёты и точки открытия общих форм.

Результат плана миграции: охват → выбранный подход и очередь → решения по формам/макетам →
конвертация и ручные доработки → пилот/откат → критерии переключения → очистка.
