# obj-lifecycle — Заполнение и проверка заполнения (справочник)

> Нормы — в `.claude/rules/1c-rules.md`. Схемы порядка и таблица «куда класть логику» — `../SKILL.md`.

## Паттерн: структура `ОбработкаЗаполнения`

Обработчик вызывается при создании объекта с данными заполнения — вводе на основании,
копировании по отбору, программном создании с передачей структуры. Устойчивая структура —
сначала специальное заполнение по типу данных заполнения, потом общее по умолчанию.

```bsl
Процедура ОбработкаЗаполнения(ДанныеЗаполнения, СтандартнаяОбработка)

    // 1. Специальное заполнение — по типу основания.
    ТипДанныхЗаполнения = ТипЗнч(ДанныеЗаполнения);

    Если ТипДанныхЗаполнения = Тип("ДокументСсылка.ЗаказКлиента") Тогда
        ЗаполнитьПоЗаказуКлиента(ДанныеЗаполнения);
    ИначеЕсли ТипДанныхЗаполнения = Тип("Структура") Тогда
        ЗаполнитьЗначенияСвойств(ЭтотОбъект, ДанныеЗаполнения);
    КонецЕсли;

    // 2. Общее заполнение — только то, что осталось незаполненным.
    Если Не ЗначениеЗаполнено(Подразделение) Тогда
        Подразделение = ПодразделениеПоУмолчанию();
    КонецЕсли;

КонецПроцедуры
```

Порядок именно такой: сначала специальное, потом общее. Иначе значения по умолчанию затрут то,
что пришло из основания.

**Не дублируй свойство метаданных «Значение заполнения».** Если `СтандартнаяОбработка` осталась
`Истина` и реквизит не заполнен обработчиком, платформа подставит значение из свойства сама
при выходе из процедуры.

## Паттерн: запрет ввода на основании

Проверка «на основании чего создавать нельзя» живёт здесь же, а не в отдельной команде ввода
на основании — иначе она обойдётся любым другим способом создания.

```bsl
Процедура ОбработкаЗаполнения(ДанныеЗаполнения, СтандартнаяОбработка)

    Если ТипЗнч(ДанныеЗаполнения) = Тип("СправочникСсылка.Сотрудники") Тогда

        Если ОбщегоНазначения.ЗначениеРеквизитаОбъекта(ДанныеЗаполнения, "ЭтоГруппа") Тогда
            ВызватьИсключение НСтр("ru = 'Ввод на основании группы сотрудников невозможен.
                |Выберите сотрудника.'");
        КонецЕсли;

        ЗаполнитьПоСотруднику(ДанныеЗаполнения);

    КонецЕсли;

КонецПроцедуры
```

Здесь именно `ВызватьИсключение`, а не `Отказ`: параметра `Отказ` у обработчика нет, а объяснить
пользователю причину надо.

Типовые случаи запрета: ввод на основании группы, когда команда одинаково доступна для групп
и элементов, и ввод на основании непроведённого документа.

## Паттерн: условная проверка заполнения

Когда обязательность реквизита зависит от условий, реквизит **удаляется** из `ПроверяемыеРеквизиты`,
а не добавляется в него. Схема: собрать массив непроверяемых, в конце вычесть его из проверяемых.

```bsl
Процедура ОбработкаПроверкиЗаполнения(Отказ, ПроверяемыеРеквизиты)

    НепроверяемыеРеквизиты = Новый Массив;

    Если Не ИННКорректен(ИНН) Тогда
        ОбщегоНазначения.СообщитьПользователю(
            НСтр("ru = 'ИНН задан неверно.'"), ЭтотОбъект, "ИНН", , Отказ);
        НепроверяемыеРеквизиты.Добавить("ИНН");
    КонецЕсли;

    Если ЮрФизЛицо <> Перечисления.ЮрФизЛицо.ФизЛицо Тогда
        НепроверяемыеРеквизиты.Добавить("ИндивидуальныйПредприниматель");
    КонецЕсли;

    ОбщегоНазначенияКлиентСервер.УдалитьЗначенияИзМассива(
        ПроверяемыеРеквизиты, НепроверяемыеРеквизиты);

КонецПроцедуры
```

**Почему нельзя наоборот.** Обратная схема — не заводить обязательность в метаданных, а добавлять
реквизит в `ПроверяемыеРеквизиты` по условию — прячет проверку от анализа: по свойству «Проверка
заполнения» в конфигураторе уже не видно, что реквизит бывает обязательным.

Оформление самого сообщения средствами БСП — скилл `use-bsp`.

## Ловушка: обработчик вызывается не при каждой записи

`ОбработкаПроверкиЗаполнения` вызывается при интерактивной записи и при явном вызове
`ПроверитьЗаполнение()`. При программной записи `Объект.Записать()` он **не вызывается**.

Практический вывод: логика, обязательная при любой записи, в этом обработчике жить не может.
Если она обязательна — её место в `ПередЗаписью`. Если она именно про заполнение формы
пользователем — оставляй здесь, но не рассчитывай на неё в интеграциях и обработках.

## Ловушка: проверка вне транзакции не видит будущего состояния

`ОбработкаПроверкиЗаполнения` выполняется **до** транзакции записи. Это хорошо — при ошибке
заполнения операция обрывается, не тронув базу. Но нового состояния объекта в базе ещё нет,
и проверка «по данным системы с учётом этого объекта» здесь невозможна.

Отсюда граница:

| Что проверяем | Где |
|---|---|
| Заполненность и корректность реквизитов самого объекта | `ОбработкаПроверкиЗаполнения` |
| Целостность объекта и зависимых данных, состояние движений, остатки | `ПередЗаписью`, `ПриЗаписи`, `ОбработкаПроведения` |

## Ловушка: несимметричная проверка

Правило, которое может быть нарушено при записи разных объектов, обязано проверяться с обеих
сторон. Если при записи подразделения проверяется, что выбранный руководитель имеет должность
«Руководитель», то при записи сотрудника нужна встречная проверка — иначе правило обходится
редактированием сотрудника. Не получается симметрично — выноси проверку из транзакции у обоих
объектов и делай её отчётом или регламентной проверкой.

## Ловушка: контроль остатков в транзакции

Проверять остаток ресурса в транзакции записи имеет смысл только если **все** документы, меняющие
этот ресурс, проверяют его так же. Достаточно одного документа, который пишет движения без
проверки, — и гарантия рушится, а цена в виде удерживаемых блокировок остаётся. В такой ситуации
контроль выносят из транзакции.
